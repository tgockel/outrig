# Crate split tradeoffs

The decisions behind `harness-components.md`, with what was rejected and why. Recorded so that
a reader who disagrees can see what was already weighed, rather than reopening it from scratch.

## Duplicate the harness, rather than move it

The agent loop is about 9,000 lines of non-test code across `llm.rs`, `llm/`, `rig_tool.rs` and
`session_tool.rs`, with roughly 4,900 lines of tests behind it.

**Chosen: copy it into `outrig` and leave `outrig-cli`'s untouched.** Work on the 0.2.x line
continues and will be merged in. Every file the move would have touched is a file that line is
still editing, so a move buys a conflict on each merge, indefinitely, in exchange for tidiness
nobody can see.

**Rejected: move it, and have `outrig-cli` depend on it.** One copy, no drift, and the right
end state. It is the right end state *later*, once the 0.2.x line has stopped moving.

**Rejected: move it gradually, file by file.** Spreads the conflicts out instead of removing
them, and leaves long stretches where a reader cannot tell which copy is authoritative.

**The cost, stated plainly:** two agent loops that diverge. A fix landing on the 0.2.x line does
not reach `outrig`'s copy unless someone carries it over. This is accepted for the duration of
the phase and is the first thing to revisit when 0.2.x quiets down.

`python/` is the exception and moves outright. It exists only on the prototype branch, so the
0.2.x line has no version of it to conflict with. The rule is about files two lines are both
editing; that is not one.

## Keep rig out of the library's public surface

`outrig-cli`'s `CliError` carries `Prompt(rig::completion::PromptError)` and
`LlmResolve(LlmResolveError)`. Every function in the harness returns `Result<_, CliError>`.

**Chosen: the library's error type converts at the boundary and exposes no rig type.** rig-core
stays a private dependency, so a rig release cannot force an `outrig` major. The conversion is
written once per variant.

**Rejected: port `CliError` as it stands.** By far the cheapest port -- every `?` keeps working
untouched -- and it makes `outrig`'s version depend on a pre-1.0 dependency's release schedule.
rig is at 0.40. That is a lot of majors to inherit.

**Rejected: decide later, since the modules are private anyway.** True today, and the reason it
was tempting. Rejected because conversions get harder to introduce once there are call sites,
and "later" has no date attached to it.

## Keep the new modules private

**Chosen: private modules in `outrig`, plus the one entry point `outrig-cli` needs to reach
them.** Private is crate-private, so something must be `pub` or the CLI cannot call the loop
either; `harness-components.md` describes how narrow that is meant to be.

The shape being copied was never designed as an API. Six of these modules are `pub` in
`outrig-cli` only under the `internal-test-api` feature, which exists so integration tests can
see them -- not so consumers can. Publishing that shape because it happens to be what exists
would commit to it by accident.

**Rejected: design the public API now.** A breaking release is the moment to do it, and the
argument is real. It loses to the fact that there is nothing to design against yet: the first
milestone is the first honest evidence about what a consumer needs.

There is a second reason to wait, and it grew stronger rather than weaker. When this was written
`outrig`'s public surface had no CI gate and `crates/outrig/public-api.txt` was regenerated by
hand. It is enforced now: `.github/workflows/ci.yml` runs a `public-api` job over
`scripts/check-public-api.py`, and the task that asked for it has landed. So a surface added here
is a surface the build will hold the line on from the first commit -- which is the right order, and
also the reason not to spend the budget on a shape that was never designed as an API.

## Add `run-new`, and rename later

**Chosen: `run` keeps its current meaning and its current code. `run-new` and `run-legacy` are
both added beside it -- the second an alias for `run`, so anyone who means to stay on the
existing system can name it explicitly before the default moves. A later milestone retargets
`run` itself.**

Adding the alias early is what makes the eventual retarget cheap for a user: by then
`run-legacy` has been the stable name for the old behavior for a while, and the switch does not
strand anyone who had been typing `run` and meaning the old thing.

Renaming `run` to `run-legacy` immediately would edit `cli/app.rs` and `cli/run.rs` -- files the
0.2.x line also edits -- for no benefit while both commands exist. Doing it at the end pays that
cost once, at a chosen moment, when the new command has earned the name.

Adding a subcommand is one enum variant, one match arm, and a reuse of the existing
`repo_cmd_ctx` preamble. Global flags are inherited. This is not the hard part of the phase.

## Branch off trunk, and never merge the prototype

**Chosen: the `version/0.3.x` branch cut from `trunk` as the long-running line for the code.
The prototype's code is ported into it; the prototype's commit is not.**

The prototype was written to answer questions, and it answered them. Its history is a record of
finding out, which is not a thing the 0.3 line needs to carry: a single commit full of
discoveries makes a poor ancestor for a branch people will be reading for a year.

These documents are not part of that. They are markdown under `plan/`, they describe a
direction rather than implement one, and 0.2.x has no competing version of them -- so they go
to `trunk` directly, through the `plan/0.3` branch and a PR for review. Holding a phase
definition hostage to the branch that implements it would make it invisible to everyone
working on the line it is meant to inform.

**Rejected: keep building on `prototype/python-exec`.** Less setup. It makes the prototype
commit the root of the release line.

**Rejected: cherry-pick the prototype commit onto the new line.** Keeps the interpreter and its 20
protocol tests exactly as proven, which is a genuine argument -- porting risks losing detail
that was hard to get right. Rejected because the code is being restructured across two crates
as it lands anyway, so it does not arrive unchanged regardless.

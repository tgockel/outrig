# 0071 -- `outrig image build` for standalone image projects

## Context

Repo-local image-configs already use `outrig build`; standalone image projects
need an equivalent command that reads project-local `image.toml`, builds the
declared image, and validates that the result is a working OutRig toolset image.

Unlike the original proposal, live validation is not optional by default. A
standalone toolset image is only useful if its declared MCP servers start and
report tools.

## Goal

Add `outrig image build` for standalone image projects, with buildah-backed
builds and default live MCP testing.

## Deliverables

- Add `outrig image build [PROJECT_DIR] [--tag <ref>] [--no-test] [--no-cache]`.
- Read `PROJECT_DIR/image.toml`; default `PROJECT_DIR` to the current directory.
- Resolve `[build].dockerfile` and `[build].context` relative to the project
  directory.
- Build with buildah and tag the image as `[image].ref`, unless `--tag <ref>`
  overrides it for that invocation.
- Preserve short image refs accepted by buildah, including `rust-dev` and
  `rust-dev:0.1.0`.
- Always validate the built image by reading `/etc/outrig/image.toml` from the
  image/container and parsing it with the standalone validator.
- By default, start the image and test every declared MCP server:
  - Initialize the server.
  - Call `tools/list`.
  - Report the number of tools returned per server.
- `--no-test` skips only the live MCP server test; it still validates the
  embedded `image.toml`.
- `--no-cache` forwards to the buildah build path consistently with existing
  repo-local image builds.
- Document command output, failure modes, `--tag`, `--no-test`, and
  `--no-cache` in the same task.

## Acceptance

- Building the project generated by `outrig image init rust-dev` succeeds.
- The command fails if `image.toml` is missing, malformed, or missing required
  standalone fields.
- The command fails if the built image does not contain `/etc/outrig/image.toml`.
- The command fails if any declared MCP server cannot initialize or cannot
  return `tools/list`, unless `--no-test` is set.
- `--tag custom-ref` uses `custom-ref` for the build output without rewriting
  `image.toml`.
- E2E tests cover the generated scaffold, embedded-file validation, live MCP
  test success, and `--no-test`.

## Dependencies

- **Hard: 0069**. Build validation uses the standalone `image.toml` parser and
  embedded image path.
- **Hard: 0070**. The init scaffold is the canonical build fixture and the
  first user-facing input to this command.

## Decisions

- **Dedicated `image::build_standalone` over a synthetic `ImageConfig`.** The
  build is a new `pub async fn build_standalone(project_dir, dockerfile,
  context, tag, no_cache)` in `image.rs`, sharing a new private
  `buildah_build_cmd` with the existing `build_image_cmd`. The `/simplify`
  dual-generation produced an alternative that instead reused `build_image_for`
  by constructing an `ImageConfig` with four dead fields; the reviewer flagged
  that this depends on `build_image_for` continuing to ignore `cfg.source()`
  (and `source()` *panics* on any field shape it doesn't expect), so the
  dedicated fn was kept to avoid that latent coupling.
- **Strict baked-file read lives in the lib** (`embedded.rs`
  `read_standalone_image_toml`): the helpers it needs --
  `process::try_capture_logged`, `process::process_error_from_output`, and the
  private `is_missing_embedded_image_config` detector + `podman_exec_root` --
  are all `pub(crate)` to `outrig`, so the strict read cannot live in the CLI.
  It is the strict sibling of the lenient `read_embedded_image_config` (which
  returns an empty config on a missing file and parses only `[mcp]`).
- **Errors use `OutrigError::Configuration`, not new typed variants.** Initial
  work added `StandaloneImageConfig{Missing,Invalid}` variants; `/simplify`
  showed these were over-engineering (nothing matches on the error -- it is only
  ever rendered as `error: {e}` -- and the ephemeral container name they carried
  is noise), so both the missing-file and parse-invalid cases map to the
  `Configuration` catch-all.
- **The live test uses the *baked* `[mcp]` map** read back from the image, not
  the on-disk copy -- this matches "validate from the image" and stays correct
  when `--tag` builds a differently-named image.
- **`--no-test` reads+validates the baked `image.toml` but skips
  `bootstrap_user` + the probe.** The strict read uses `podman exec --user=0:0`
  (`cat`), which works before bootstrap; only the live MCP exec needs the host
  user materialized.
- **Teardown is capture-result -> stop -> propagate** (validation error wins
  over a stop error); `Container`'s `Drop` is the backstop for the window
  between `start` and `stop`. A single throwaway tempdir backs both the
  `/workspace` bind mount and the per-server MCP stderr logs; the happy-path
  logs are discarded because startup / `tools/list` failures are already
  enriched into the returned error.
- **No standalone build cache.** A standalone build tags a caller-named ref
  (e.g. `rust-dev`), not a content-addressed `outrig-cache:<key>`, so there is
  no project-level cache to probe; `--no-cache` only forwards `--no-cache` to
  buildah.
- **Disk-gate failures are unit-tested without podman.** `load_project_image_toml`
  (missing / malformed / missing-`ref`) runs in the standard `cargo test`; the
  build, embedded validation, live-test success, `--no-test`, `--tag`
  preservation, and MCP-startup-failure paths are covered by the gated
  `tests/image_build.rs` e2e suite.

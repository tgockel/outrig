# 0002-54 -- Release 0.2.0

## Context

The queue up to here fixes the blockers, corrects the docs, cuts `0.2.0-rc.3` (0002-52), and gathers
live runtime evidence (0002-53). Then it stopped. Nothing joined those two into a final release, and
the two tasks nearest the end actively contradict each other if read as the end: 0002-49 was written
to produce final `[0.2.0]` documentation, while 0002-52 explicitly cuts an RC, says it is not final,
and requires integration time afterward. Something has to own the decision that the integration
time was enough, and the mechanics that follow it.

That is this task. It is deliberately last, deliberately gated on a judgment rather than on a
test, and deliberately separate from 0002-52 so that a second RC -- if rc.3 exposes another
public-surface correction -- costs one more pass through 0002-52 rather than a rewrite of the final.

The audit's own sequencing says the same thing: cut rc.3, exercise it, "release 0.2.0 only after
rc.3 gets integration time with no further public-surface corrections."

## Goal

0.2.0 published from a tree whose public surface has not moved since rc.3, with the release
mechanics done in the order `RELEASING.md` requires.

## The exit criteria

Written down in advance, not judged afterward. The release proceeds only if all hold:

- **No public-surface change since rc.3.** `crates/outrig/public-api.txt` and
  `crates/outrig-cli/public-api.txt` are byte-identical to the rc.3 tag under 0002-48's pinned
  toolchain. A single moved line means another RC, not a judgment call about severity.
- **0002-53's evidence exists** for both architectures and is green, including 0002-37's live tier.
- **No open defect of the class 0002-52's record calls blocking.** That class is defined in
  0002-52's `## Decisions`; this task checks membership against it rather than re-deciding what
  counts. There is deliberately no soak window and no qualifying-use test to satisfy -- 0002-52
  considered both and recorded why they measure nothing here.

If any fails, the outcome is a new RC through 0002-52, and this task waits.

## Deliverables

- **The rc.3 -> 0.2.0 bump**: `[workspace.package]` in the root `Cargo.toml` and the `outrig`
  requirement in `crates/outrig-cli/Cargo.toml`, which must drop the pre-release from the pin.
- **Final documentation**, the half 0002-49 deliberately did not write because it can only be
  written once:
  - dated `[0.2.0]` headings in both changelogs, with tag links pointing at `outrig-v0.2.0` and
    `outrig-cli-v0.2.0`, folding rc.1 + rc.2 + `Unreleased` into one section per crate;
  - the migration checklist 0002-49 drafted, promoted into that section;
  - the quickstart's sample `outrig --version` output;
  - `SECURITY.md`'s supported-version prose and table, which `RELEASING.md`'s **Refresh the
    version-bearing docs** step says to skip
    for a pre-release and therefore has been skipped through three RCs;
  - no file describing 0.2.0 as a candidate.
- **Final package validation**, re-run rather than assumed to still hold: 0002-48's snapshot
  gate, the combined `cargo publish --dry-run -p outrig -p outrig-cli`, and a
  `cargo package` under `OUTRIG_REQUIRE_ENTER=1` (0002-52's `package` job) so the published
  archive is proved to build its own launcher.
- **Publication in dependency order** -- `outrig`, then `outrig-cli` once the index has caught up
  -- followed by the post-publish `cargo install outrig-cli` smoke test, the two tags, and the
  GitHub release, per `RELEASING.md`'s **Dry-run both crates in one
  invocation** through **Smoke-test the published artifact**.

## Acceptance

- The exit criteria above are each recorded as met, with the evidence, in this task's
  `## Decisions`. "We felt it was ready" is not a record.
- **The release record states gate item 17 as partially met.** 0002-48 accepted the downstream
  runtime-core surface test as a deliberate exception, so a note claiming the 18-item gate was
  completed in full would be false. Carry the waiver forward with its reason.
- `cargo install outrig-cli --version 0.2.0 --locked` into a clean `CARGO_HOME` and a clean
  `--root` yields a binary reporting `0.2.0`, and the resolved `outrig` is `0.2.0` **from
  crates.io** -- assert the source, not just the version, or a stale local path satisfies it.
- Both tags exist and match the changelog links.
- **No *active* artifact describes a release candidate**: the two manifests and the lockfile, the
  current changelog headings and their tag links, the quickstart's version output,
  `SECURITY.md`'s supported-version table, and the release announcement. Historical changelog
  sections, `RELEASING.md`'s pre-release guidance, `plan/done/` entries, and this task all
  discuss RCs legitimately and are out of scope -- "nothing in the tree says `rc`" was an earlier
  draft's criterion and could never have passed.
- The published `outrig` crate contains `src/container/enter/launcher.rs`, which `build.rs`
  compiles at build time -- check the actual `.crate` archive, since the project's constraint is
  that `cargo install` builds every feature from source with no prebuilt binaries.

## Design forks

1. **How long the soak is -- Closed by 0002-52: there is no soak.** A window defined by who had
   installed rc.3 from crates.io measures nothing when the maintainer installs from git, and
   `outrig-cli` is not published at an RC at all. What survived is the blocker class, which is
   the part that decides anything. See 0002-52's `## Decisions`.

2. **What counts as a public-surface change worth another RC -- Recommended: any.** A byte-diff
   in the snapshot is a bright line and cheap to check. Softening it to "any *breaking* change"
   reintroduces the judgment call this task exists to avoid, and 0002-48 exists precisely because
   the snapshot has silently rotted before.

## Dependencies

- **Hard: 0002-52** -- there is no final without the RC it cuts.
- **Hard: 0002-53** -- the runtime evidence is an exit criterion.
- **Hard: 0002-48** -- the snapshot comparison is only meaningful under a pinned toolchain.

## Decisions

1. **Exit criterion 1 -- no public-surface change since rc.3: met, by byte-diff and by
   regeneration.** `git diff outrig-v0.2.0-rc.3 HEAD` over `crates/outrig/public-api.txt` and
   `crates/outrig-cli/public-api.txt` is empty. That the committed files are unmoved is
   necessary but not sufficient -- they could both be stale -- so `python3
   scripts/check-public-api.py` was re-run under 0002-48's pin (`nightly-2026-05-06`,
   `cargo-public-api 0.52.0` locked) and reported `OK` for both. Eight commits separate rc.3
   from this one, including one `feat:`; none of them moved a public item.

2. **Exit criterion 2 -- 0002-53's evidence: met, on both architectures.** CI run
   `35912249747` on `0c583523` is green across `live-e2e (x86-64)`, `live-e2e (aarch64)`,
   `public-api`, `package`, all three `cargo` rows, `fmt`, `doc-style`, `links`, and `mdbook`.
   0002-37's live tier is inside that suite rather than beside it, so a green `live-e2e` row is
   what carries it.

3. **Exit criterion 3 -- the nft defect is in the blocker class, and is being waived anyway.
   This is the one exception in the release, and it is the maintainer's call, not a reading
   this task derived.** The facts are not in dispute. 0002-52 recorded the trigger as *"Any of
   these found in rc.3 means another candidate through this task rather than a judgment call
   about severity … any security-semantics defect"*. The interceptor defect 0002-53 found --
   `nft` 1.0.9 parsing a `create table … { … }` block, exiting zero, and silently installing an
   empty table, so `audit` recorded nothing and `filter` refused nothing -- was found in rc.3
   and is a security-semantics defect. Three places in the tree say so: 0002-53's `##
   Decisions` item 4 (*"`0002-54` should treat it as such"*), `plan/todo/README.md`, and commit
   `ad59179e`'s message.

   **This task supersedes those three statements rather than disagreeing with them silently.**
   The trigger is keyed on *discovery* (`found in rc.3`); this task's own criterion is keyed on
   *persistence* (`no open defect`). Where they diverge, the release adopts the second, on
   these grounds:

   - the defect is fixed in trunk, by `ad59179e`, which landed 4 hours after the rc.3 tag;
   - the fix carries a regression test that asserts the *shape* of the generated script rather
     than its content, which is the property the old test could not see;
   - the live tier that found it now runs per PR on x86-64 and AArch64, and is green on the
     commit being released -- so the fix is covered by the same mechanism that exposed the bug;
   - the public surface has not moved a byte since rc.3, so no consumer's code changes;
   - the maintainer has been running the CLI and the library from git through the interval and
     judges it good.

   **What this costs, stated plainly:** 0.2.0 ships a runtime that no published candidate ever
   carried. rc.3 is the last published artifact, and eight commits -- a security fix, a
   lifecycle fix, a new `outrig clean --session` flag, and four smaller fixes -- sit between it
   and this release. The blocker class existed precisely to prevent that, and accepting it here
   means the class did not decide this release. Anyone reading this later should read it as a
   waiver, not as evidence that the rule was satisfied.

   **The rule is not weakened for next time.** It is unchanged and still keyed on discovery; a
   future task hitting the same trigger inherits the same obligation and the same need to say
   so out loud if it declines.

4. **Gate item 17 ships partially met, and the note that says otherwise would be false.**
   0002-48 delivered snapshot enforcement and deferred the downstream runtime-core surface test
   (`plan/next/container-surface-test.md`) as an accepted release exception, on the reasoning
   that the surface is not untested but untested *as a whole*: the composed path -- acquire an
   image, start a container from a spec, exec a server over it, aggregate through `ProxyServer`,
   tear down -- has no test driving it the way a downstream crate would. A snapshot proves the
   shape did not move; it does not prove the shape is still usable. That gap is carried into
   0.2.0 open, and the 18-item gate is **17 met and one partial**, not 18 met.

5. **The changelog fold re-bases every entry onto 0.1.0, which is what could only be written
   once.** Each candidate section was written measured against the candidate before it, so
   concatenating them would have produced a record no 0.1 consumer could read. Four
   consequences, each applied by hand after the mechanical regroup:

   - the three per-candidate ledes are dropped, not merged. Everything they summarized -- rmcp
     1.x -> 3.1, MSRV 1.88, the `#[non_exhaustive]` sweep -- is in **Migrating from 0.1**,
     which is the ordered list that replaces them;
   - 0002-49's `Workspace` correction is folded into the entry it corrects. It existed as a
     separate entry only because rewriting published rc.2 text was off-limits; once both live
     in one section, a claim and its correction side by side is a contradiction, so the
     corrected statement is now the entry and the meta-entry is gone;
   - cross-references to candidate sections that no longer exist are rewritten to name the
     thing rather than the release (`the same trade the Workspace accessors took`);
   - three factual notes measured against a candidate are re-based onto 0.1, and one
     candidate-relative behavioral claim is restated as a claim about the emitted command.

   The one surviving mention of a candidate is deliberate: `from_config`'s migration note warns
   a reader who arrived through a published 0.2 candidate that the compiler will flag nothing.
   The library's candidates *were* published, so that reader exists. The acceptance criterion
   bars an active artifact describing 0.2.0 *as* a candidate, which this does not.

6. **`outrig-cli` 0.2.0-rc.1 was never tagged and never published, so its changelog section was
   a record of nothing.** `plan/next/cli-changelog-has-no-rc2-section.md` could not settle this
   without the remote and routed it here. Both halves are now answered: `gh api
   repos/tgockel/outrig/tags` lists no `outrig-cli-v0.2.0-rc.*`, and crates.io lists exactly
   one `outrig-cli` version, `0.1.0`. The section also told readers to run `cargo install
   outrig-cli --version 0.2.0-rc.1`, which could never have worked. Folding it into `[0.2.0]`
   removes the heading, the dead tag link, and the impossible instruction together, so the
   entry is deleted rather than carried.

7. **The version-bearing docs are refreshed in the release commit, ahead of publication.**
   `RELEASING.md` puts **Refresh the version-bearing docs** after **Publish**, because for a
   pre-release the step is skipped entirely and a bare `cargo install` should go on describing
   the latest stable. Doing it before publication here is a deviation with a reason: the whole
   tree is being prepared for handover in one commit, and a `SECURITY.md` claiming `0.1.x` is
   supported is wrong from the moment 0.2.0 exists rather than from the moment someone
   remembers to amend it. These are the docs that have been skipped through three candidates.

8. **`plan/next/accept-loop-tests-write-no-audit-records.md` is answered, not inherited.** Its
   open question was whether two deterministically failing lib tests indicted the `AuditSink`
   write path or the sandbox. Both halves of the check it asked for now agree: CI run
   `35912249747` logs both names passing in a `423 passed; 0 failed` row, and the same two run
   outside the sandbox on this machine in 0.18 s against a 30 s poll timeout inside it. So the
   tests depend on ambient conditions they do not state, and `AuditSink` is exonerated. This
   mattered to the release rather than being a passing observation: an empty audit log is the
   same symptom as the defect being waived in decision 3, and signing that waiver with two
   unexplained empty-audit-log failures on the bench would have been signing it blind. The
   entry stays open for the test-hygiene fix.

9. **Outstanding at landing: everything downstream of `cargo publish`.** The task lands with
   its local deliverables complete and verified -- version bump, both folds, the version-bearing
   docs, the snapshot gate, `cargo publish --dry-run -p outrig -p outrig-cli`, and `cargo
   package` under `OUTRIG_REQUIRE_ENTER=1` with `src/container/enter/launcher.rs` confirmed
   present in `outrig-0.2.0.crate`. Publication itself is the maintainer's, so four acceptance
   criteria are **not** met at landing and are not claimed to be: the `cargo install
   outrig-cli --version 0.2.0 --locked` smoke test into a clean `CARGO_HOME` asserting the
   resolved `outrig` came from crates.io, the existence of `outrig-v0.2.0` and
   `outrig-cli-v0.2.0`, the changelog tag links resolving, and the GitHub release. The phase
   README stays in `plan/phase/` for the same reason -- 0002 closes when 0.2.0 is on crates.io,
   not when the commit that prepares it exists.

# 0002-52 -- Cut a fresh RC, and make the packaging check able to catch this

## Context

### The tree claims a version that is already published

The root manifest says `version = "0.2.0-rc.2"` (`Cargo.toml:6`), inherited by both crates. That
version is on crates.io and is immutable. Meanwhile the CLI's source has moved on and imports a
library symbol added after that publication.

So an install-shaped consumer -- one that resolves `outrig` from the real index rather than from
a local path -- fails: the newly packaged CLI compiles against the published rc.2 library and
hits an unresolved import, or, with the packaged lock, detects a checksum mismatch.

### The existing check cannot see it

`RELEASING.md`'s **Dry-run both crates in one invocation** step runs:

```sh
cargo publish --dry-run -p outrig -p outrig-cli
```

and the file itself explains why that passes: "Cargo packages both, unpacks `outrig` into a
temporary registry under `target/package/`, and verify-builds `outrig-cli` against that packaged
copy". The temporary registry holds the *current local* library at the *same version number*, so
the published rc.2 is never consulted. The masking is structural -- the check is doing exactly
what it was designed to do, and that design cannot detect a version that was already cut.

### Strict rustdoc fails

`cargo rustdoc -p outrig --lib --locked -- -D warnings` fails on five unresolved or private
intra-doc links. Nothing in CI runs it, so it has drifted.

## Goal

A candidate version that has never been published, a packaging check that would have caught the
collision, and clean strict rustdoc gated in CI.

## Deliverables

- **Bump to `0.2.0-rc.3`**: `[workspace.package]` in the root `Cargo.toml`, and the
  `outrig = { path = "../outrig", version = "..." }` requirement in
  `crates/outrig-cli/Cargo.toml`. Pre-releases need the exact pre-release in the pin, which
  `RELEASING.md`'s pre-release section already documents. **Never reuse rc.2.**
- **A guard that the candidate version is absent from crates.io**, run before the dry-run. A
  version already on the index is a hard stop, not a warning -- this is the check whose absence
  produced the current state.
- **One reproducible install-shaped check, specified rather than gestured at.** Package both
  crates; seed a local registry with the two archives; `cargo install` the CLI candidate **from
  that registry** with path overrides disabled, a clean `CARGO_HOME`, a clean `--root`, and
  `--locked`; assert from `cargo metadata` (or the resulting lockfile) that `outrig` resolved
  from the registry at the candidate version and not from a path; then run the installed binary
  and assert its `--version`. Each of those clauses is load-bearing -- a path override or a warm
  `CARGO_HOME` silently reintroduces the masking this check exists to remove.
- **Keep the two checks distinct.** Pointing the version guard at the published rc.2 is the
  *negative* regression: it proves the collision detector works. The install-shaped check above
  is the *positive* one: it proves rc.3 actually resolves and runs. Neither substitutes for the
  other, and a post-publish `cargo install` is an additional smoke gate rather than a
  pre-publish substitute for either.
- **Package-content CI.** `plan/next/ci-configuration-coverage.md` wanted a `cargo package` /
  `publish --dry-run` job because `crates/outrig/build.rs` compiles
  `src/container/enter/launcher.rs` at build time, so the published crate must ship that file and
  nothing enforces it. A manual dry run in `RELEASING.md` does not cover that -- it runs when
  someone releases, not when someone adds an `exclude`. Either add the CI job here or correct
  that buffer entry to say the item stayed there.
- **Fix the five rustdoc links** and add `cargo rustdoc -p outrig --lib --locked -- -D warnings`
  to `.github/workflows/ci.yml`. This one belongs in per-PR CI -- unlike the API snapshot
  (0002-48), it depends on nothing that churns between nightlies.
- **`RELEASING.md` gains both new steps**, positioned before the publish.
- **The soak record from fork 2**, written into this task's `## Decisions` before rc.3 is
  published, so 0002-54 has something to check rather than something to compose.

## Acceptance

- The candidate version is `0.2.0-rc.3` in both packaged manifests and in the CLI's `outrig`
  requirement, asserted from `cargo metadata` and the packaged `Cargo.toml` files rather than by
  grepping the working tree -- the working tree is not what gets published.
- The version guard fails when pointed at an already-published version -- test it against
  `0.2.0-rc.2`, which is the known-bad case and the reason the guard exists.
- **The guard fails closed.** A registry query that errors, times out, or is rate-limited must
  stop the release, not read as "version absent". This is the difference between a guard and a
  guard-shaped comment.
- The install-shaped check passes, and its assertions come from `cargo metadata`, the lockfile,
  and the installed binary's output.
- `cargo rustdoc -p outrig --lib --locked -- -D warnings` exits clean, and CI runs it.
- `cargo publish --dry-run -p outrig -p outrig-cli` still passes, and the install-shaped check
  passes independently of it.
- This is an **RC, not final.** The audit's sequencing is explicit: cut rc.3, give it integration
  time, and release 0.2.0 only if no further public-surface corrections are needed. Do not
  collapse this task into a final tag.

## Design forks

1. **Which local-registry tooling to use -- Open, and that is all that is open.** The registry is
   seeded with the two *candidate* archives; `cargo-local-registry`, a vendored index, or a
   hand-rolled directory registry all work, and the choice is about maintenance rather than
   semantics. An earlier draft of this fork proposed seeding with the *published* library and
   offered post-publish `cargo install` as a substitute. Both are wrong and are recorded here so
   they are not re-proposed: no published rc.3 exists before the positive check, and a
   post-publish install cannot gate a publication that already happened.

2. **The soak parameters, decided here rather than at 0002-54 -- Open, and answer it before rc.3
   ships.** How long the integration window runs, what counts as qualifying use (someone actually
   installing rc.3, not elapsed days), where the evidence lives, and what class of defect resets
   the clock. Writing these down after the fact is how a soak becomes "it felt fine". 0002-54
   consumes this record; it must not be the one to invent it.

## Dependencies

- **Hard: after 0002-37 through 0002-49.** A version cut is only meaningful once the blockers are
  fixed and the notes describe what ships.

## Decisions

1. **Fork 1 is moot, because the scripts it chooses tooling for were removed.** Both deliverables
   -- the crates.io version guard and the install-shaped check -- were built, measured against
   what `cargo publish` already does, found to duplicate almost all of it, and deleted. What
   replaced them is a `package` CI job of three steps:

   ```yaml
   env:
     OUTRIG_REQUIRE_ENTER: "1"
   ...
   - run: cargo package --locked -p outrig -p outrig-cli
   ```

   The reasoning, recorded because the deliverables argue the opposite at length and should not
   be re-proposed from that text:

   - **A version already published.** `cargo publish` refuses it and names it. A guard buys
     finding out before the verify build rather than after -- minutes, not a bad release.
   - **A stale or unresolvable dependency pin.** `cargo publish --dry-run -p outrig -p
     outrig-cli` verify-builds the CLI against the packaged library with `path` stripped, which
     is the case that matters. Publishing the crates separately resolves against the real index
     directly.
   - **The archive missing a file the build needs.** *This is the only real gap*, and it is not
     cargo's to close: `crates/outrig/build.rs` degrades a launcher it cannot compile -- sources
     absent included -- to a cargo warning and an empty artifact, so the verify build goes green
     and every `view = "primary"` sidecar breaks after release. `OUTRIG_REQUIRE_ENTER=1` makes
     that a build error, and `cargo package` applies it to the packaged archive rather than the
     working tree. Confirmed by excluding `src/container/enter/launcher.rs` and watching
     `cargo package` fail with "compiling the filesystem-view helper failed (OUTRIG_REQUIRE_ENTER
     is set)" / "failed to verify package tarball".

   The behavioral check is also *stronger* than what was removed, which asserted a file list: it
   proves the launcher still compiles out of the archive, which is what the file is for.

2. **A claim this task made in support of the install check is false, and is recorded so it is
   not repeated.** The argument was that a stale pin -- `outrig = "0.2.0-rc.2"` while cutting
   rc.3 -- packages cleanly and "would publish a CLI resolving the published rc.2 off the real
   index". It would not. Cargo resolves a requirement to the *highest* matching version;
   measured, a crate requiring `outrig = "0.2.0-rc.1"` locks `0.2.0-rc.2`. A stale pre-release
   pin publishes a requirement looser than intended, which costs precision and not correctness,
   and only bites under `-Z minimal-versions` or if the newer version is yanked. This was the
   strongest evidence offered for the install-shaped check and it does not hold.

3. **Fork 2 -- there is no soak policy, and that is the decision. Only the blocker class
   survives.** The fork asks for a window, a qualifying use, an evidence source and a blocker
   policy. A draft supplied all four: seven days minimum, closing only once OutRig had been run
   from a *published* rc.3 installed with `cargo install outrig-cli --version 0.2.0-rc.3`.

   That was rejected on its premise. `outrig-cli` can be installed straight from git, so a
   window keyed on who had installed it from crates.io measures nothing the maintainer cannot
   already get. It was circular besides: the only reason to publish `outrig-cli` at an RC at all
   was to make that install possible, so the policy manufactured its own precondition.

   **What remains is the blocker class**, which is the only part that decides anything. Any of
   these found in rc.3 means another candidate through this task rather than a judgment call
   about severity:

   - any defect requiring a public-surface change -- one that would move either
     `public-api.txt` by a byte;
   - any container or lifecycle leak;
   - any security-semantics defect.

   `0002-54` checks membership against that list. Its third exit criterion, which required
   satisfied soak parameters, is deleted rather than left pointing at a record that does not
   exist; its fourth already named this class and now carries the criterion alone. The phase
   README's fourth exit criterion is rewritten the same way.

   **rc.3 is therefore a library-only cut, as rc.1 and rc.2 were.** `244485b4` states the
   practice: "The cut is library-only, as rc.1 turned out to be: only outrig-v0.2.0-rc.1 was
   ever tagged, and outrig-cli keeps accumulating under its own [Unreleased] while inheriting
   the workspace version." So `outrig-cli`'s changelog keeps `[Unreleased]`, there is no
   `outrig-cli-v0.2.0-rc.3` tag, and `RELEASING.md` now says so -- it was practice written down
   nowhere, and its absence is what let an intermediate draft publish the CLI by accident.

4. **The task's "five unresolved or private intra-doc links" was seven** -- two
   `broken_intra_doc_links` and five `private_intra_doc_links`. The count in the task body
   predates `network.rs`'s two, which `plan/next/private-intra-doc-links-regressed.md` also
   missed. All seven became plain backticked text rather than links.

   `ResolvedNames` and `ClientAssertion` were deliberately *not* made public to satisfy their
   links. Publishing two types to fix a doc warning would move `crates/outrig/public-api.txt`
   in the very commit that cuts the candidate, and a byte diff in that file is what `0002-54`'s
   first exit criterion is watching for. `launcher.rs` and `elf` could not have been linked in
   any case: the first is a `rustc` input `build.rs` compiles rather than an item, and the
   second is `#[cfg(test)]`, so it does not exist in a rustdoc build at all.

5. **The rustdoc guard is `cargo rustdoc -p outrig --lib`, in the `cargo` job, not
   `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps` in `doc-style`.** That is a deviation from
   what `private-intra-doc-links-regressed.md` proposed, for two reasons: `doc-style` installs
   no toolchain and exists to run a Python auditor over `doc/`, and a workspace-wide
   `cargo doc` collides the two crates' output names -- a separate known problem, and not one
   to take on here. The `if: matrix.name == 'default'` guard is the established "one row pays
   this" pattern and reuses a warm cache. Both retired entries were deleted;
   `0002-48`'s `## Decisions` still names the second one, and that reference was left alone --
   a landed task's record is history, not a document to keep current.

## Decisions from the /simplify pass

A review pass ran over the change while the two scripts still existed; six of its eight findings
were about code that has since been deleted, and went with it. Two outlived it.

1. **Strict rustdoc covers `outrig-cli` too.** The guard was first scoped to `-p outrig --lib`
   on the grounds that a workspace-wide run collides output names. True of `cargo doc
   --workspace`, whose *binary* target `outrig` collides with the library crate -- but it does
   not justify the narrowing, since two `--lib` invocations render `outrig` and `outrig_cli` and
   cannot collide. `outrig-cli`'s lib is a published surface with its own intra-doc links and
   was unchecked. It is clean today, which is only knowable because it is now run. The collision
   itself is filed as `plan/next/workspace-rustdoc-output-collision.md`, which
   `plan/todo/README.md` had recorded as wanting an entry.

2. **Noted, not changed: `network.rs:1885` still carries a live `` [`ClientAssertion`] ``
   link.** It sits on a private item, so the lint does not fire and the file now spells the same
   reference two ways. Under 0001-52's rule ("private targets are implementation details,
   demote them") it would also be demoted; under the rule this task adopts -- whatever rustdoc
   denies under `-D warnings` -- it stays. The second rule is the better one, because a
   private-to-private link is useful in a `--document-private-items` build, and because it is
   machine-checked rather than taste.

# 0033 -- `outrig init`

## Goal

Idempotent end-to-end setup orchestrator. Detects which pieces are missing and runs the
specific subcommand for each: [`outrig config init`](../../doc/usage/config.md) for the global
config, an inline repo-config phase for `.agents/outrig/config.toml`, and
[`outrig container add`](../../doc/usage/container.md) in a loop for the first (and any
further) container-configs.

## Deliverables

- `src/init/mod.rs::run(force: bool) -> Result<()>` matching `doc/usage/init.md`.
- Three phases, each independently skippable:
  - **Global config phase**: if `~/.outrig/config.toml` is missing, call
    `config::init::run(force)`. If present, log `[outrig] using existing global config at
    <path>` and skip.
  - **Repo config phase**: ensure `.agents/outrig/` exists (`fs::create_dir_all`,
    idempotent). If `.agents/outrig/config.toml` is missing, prompt for:
    - Workspace `host-path` (default `.`), `container-path` (default `/workspace`).
    - Default agent name (default `coding`).
    - "Override default-model for this agent? [y/N]" -- if yes, prompt for model name.
    - Preamble (default `"You are a careful coding assistant."`).
    Set `default-container` and `default-agent` to the agent name (so the next phase scaffolds
    a matching container-config). Render and write atomically.
    If `.agents/outrig/config.toml` already exists, skip.
  - **Container loop**: prompt `Add a container-config now? [Y/n]`. On yes, call
    `container::add::run(None, force)`; then loop with `Add another? [y/N]`. On no, exit.
- Atomic writes via `tempfile::NamedTempFile::persist` so an interrupted prompt never leaves
  a half-written config.
- `--force` propagates to both nested calls (`config::init::run`, `container::add::run`).
- `tests/init_scripted.rs`: drive `init` end-to-end in a tempdir against a scripted stdin
  stream; cover two scenarios:
  - Fresh state -- everything written; assert configs parse + validate via 0005's loader.
  - Re-run on a fully-set-up repo with the container-loop answered "no" -- nothing is
    rewritten; exit code 0.

## Acceptance

- `cargo test init_scripted` passes (configs parse + validate; idempotent re-run leaves the
  filesystem unchanged).
- Manual: from a fresh empty git repo, `outrig init` walks through prompts and produces a
  configuration that subsequent `outrig run` (with `OPENAI_API_KEY` set) launches successfully
  end-to-end.
- Drop the `> TODO: Incomplete` markers on `doc/usage/init.md` and `doc/quickstart.md`.

## Notes

- The nested calls into `config::init::run` and `container::add::run` are function calls
  within the same process -- not `Command::new("outrig")` re-exec.
- Idempotency is the headline behavior: a user re-running `outrig init` after a successful
  setup should see "nothing to do" for the first two phases and only be prompted about
  adding another container.
- The repo-config phase lives inline (rather than in a separate `outrig config repo-init` or
  similar) because it's small, repo-specific, and naturally runs once per repo.

## Decisions

- **Repo-config bootstrap is shared with `container add`.** `init::repo::ensure` (used by
  `init::run_with`) and `init::repo::resolve_or_bootstrap` (used by `container::add::run`)
  share one private `write_repo_config`. Running `outrig container add` in a fresh repo
  prompts `Configure outrig in this directory now? [Y/n]`; on yes the same repo-config
  prompts run, on no it returns `OutrigError::NoRepoConfig` so the exit code/error string
  match the previous behavior.
- **`--force` does not propagate to the repo-config phase.** Phase 2 has no `force`
  parameter: there's no safe semantic for clobbering an existing repo `config.toml`
  (it can hold tuned `[containers.*]` blocks `init` knows nothing about). `--force` still
  propagates to phase 1 (`config::init::run_with`) and phase 3 (`container::add::run_with`).
  Users who want to rewrite the repo config delete it explicitly.
- **One `PromptSource` is threaded through all three phases.** `init::run_with` builds
  one `prompt::auto()` and passes it to `config::init::run_with`, `repo::ensure`, and the
  `container::add::run_with` loop. Scripted-stdin tests drive the whole flow with one byte
  stream. The `_with` variants are the canonical test seam; the bare `run` wrappers in
  each module construct real terminal I/O for binary callers.
- **Repo-config rendering reuses `Config`.** Rather than maintain a parallel set of view
  structs, `init::repo::render` populates a `Config` (with `..Config::default()`) and uses
  the existing `skip_serializing_if` rules. `Workspace::default()` supplies the prompt
  defaults so the two locations cannot drift.
- **`container add`'s `run` is the only binary entry.** It now takes `cwd` and does its
  own resolve+bootstrap+`run_with` internally; `bin/outrig.rs` calls it as a one-liner.
- **`?`-help wired into TTY bool/string prompts.** Dialoguer's `Confirm` widget silently
  re-prompted on any non-y/n input, so typing `?` looked like "nothing happened".
  Replaced it with `Input::<String>` + manual y/n parsing, matching the line-based mode's
  `?`-shows-help / bad-input-shows-error semantics. While here, dropped the proactive
  `description`-as-preamble for `ask_string` / `ask_bool` -- with `?` working, the
  preamble was redundant context. `description` is now `?`-only help across both modes
  for those two prompt types. Select / multiselect still show the preamble (dialoguer's
  widgets don't expose a `?` hook there).

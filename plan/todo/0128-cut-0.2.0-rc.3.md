# 0128 -- Cut a fresh RC, and make the packaging check able to catch this

## Context

### The tree claims a version that is already published

The root manifest says `version = "0.2.0-rc.2"` (`Cargo.toml:6`), inherited by both crates. That
version is on crates.io and is immutable. Meanwhile the CLI's source has moved on and imports a
library symbol added after that publication.

So an install-shaped consumer -- one that resolves `outrig` from the real index rather than from
a local path -- fails: the newly packaged CLI compiles against the published rc.2 library and
hits an unresolved import, or, with the packaged lock, detects a checksum mismatch.

### The existing check cannot see it

`RELEASING.md` step 4 runs:

```sh
cargo publish --dry-run -p outrig -p outrig-cli
```

and the file itself explains why that passes: "Cargo packages both, unpacks `outrig` into a
temporary registry under `target/package/`, and verify-builds `outrig-cli` against that packaged
copy". The temporary registry holds the *current local* library at the *same version number*, so
the published rc.2 is never consulted. The masking is structural -- the check is doing exactly
what it was designed to do, and that design cannot detect a version that was already cut.

### Strict rustdoc fails

`cargo rustdoc -p outrig --lib --locked -- -D warnings` fails on five unresolved or private
intra-doc links. Nothing in CI runs it, so it has drifted.

## Goal

A candidate version that has never been published, a packaging check that would have caught the
collision, and clean strict rustdoc gated in CI.

## Deliverables

- **Bump to `0.2.0-rc.3`**: `[workspace.package]` in the root `Cargo.toml`, and the
  `outrig = { path = "../outrig", version = "..." }` requirement in
  `crates/outrig-cli/Cargo.toml`. Pre-releases need the exact pre-release in the pin, which
  `RELEASING.md`'s pre-release section already documents. **Never reuse rc.2.**
- **A guard that the candidate version is absent from crates.io**, run before the dry-run. A
  version already on the index is a hard stop, not a warning -- this is the check whose absence
  produced the current state.
- **One reproducible install-shaped check, specified rather than gestured at.** Package both
  crates; seed a local registry with the two archives; `cargo install` the CLI candidate **from
  that registry** with path overrides disabled, a clean `CARGO_HOME`, a clean `--root`, and
  `--locked`; assert from `cargo metadata` (or the resulting lockfile) that `outrig` resolved
  from the registry at the candidate version and not from a path; then run the installed binary
  and assert its `--version`. Each of those clauses is load-bearing -- a path override or a warm
  `CARGO_HOME` silently reintroduces the masking this check exists to remove.
- **Keep the two checks distinct.** Pointing the version guard at the published rc.2 is the
  *negative* regression: it proves the collision detector works. The install-shaped check above
  is the *positive* one: it proves rc.3 actually resolves and runs. Neither substitutes for the
  other, and a post-publish `cargo install` is an additional smoke gate rather than a
  pre-publish substitute for either.
- **Package-content CI.** `plan/next/ci-configuration-coverage.md` wanted a `cargo package` /
  `publish --dry-run` job because `crates/outrig/build.rs` compiles
  `src/container/enter/launcher.rs` at build time, so the published crate must ship that file and
  nothing enforces it. A manual dry run in `RELEASING.md` does not cover that -- it runs when
  someone releases, not when someone adds an `exclude`. Either add the CI job here or correct
  that buffer entry to say the item stayed there.
- **Fix the five rustdoc links** and add `cargo rustdoc -p outrig --lib --locked -- -D warnings`
  to `.github/workflows/ci.yml`. This one belongs in per-PR CI -- unlike the API snapshot
  (0125), it depends on nothing that churns between nightlies.
- **`RELEASING.md` gains both new steps**, positioned before the publish.
- **The soak record from fork 2**, written into this task's `## Decisions` before rc.3 is
  published, so 0130 has something to check rather than something to compose.

## Acceptance

- The candidate version is `0.2.0-rc.3` in both packaged manifests and in the CLI's `outrig`
  requirement, asserted from `cargo metadata` and the packaged `Cargo.toml` files rather than by
  grepping the working tree -- the working tree is not what gets published.
- The version guard fails when pointed at an already-published version -- test it against
  `0.2.0-rc.2`, which is the known-bad case and the reason the guard exists.
- **The guard fails closed.** A registry query that errors, times out, or is rate-limited must
  stop the release, not read as "version absent". This is the difference between a guard and a
  guard-shaped comment.
- The install-shaped check passes, and its assertions come from `cargo metadata`, the lockfile,
  and the installed binary's output.
- `cargo rustdoc -p outrig --lib --locked -- -D warnings` exits clean, and CI runs it.
- `cargo publish --dry-run -p outrig -p outrig-cli` still passes, and the install-shaped check
  passes independently of it.
- This is an **RC, not final.** The audit's sequencing is explicit: cut rc.3, give it integration
  time, and release 0.2.0 only if no further public-surface corrections are needed. Do not
  collapse this task into a final tag.

## Design forks

1. **Which local-registry tooling to use -- Open, and that is all that is open.** The registry is
   seeded with the two *candidate* archives; `cargo-local-registry`, a vendored index, or a
   hand-rolled directory registry all work, and the choice is about maintenance rather than
   semantics. An earlier draft of this fork proposed seeding with the *published* library and
   offered post-publish `cargo install` as a substitute. Both are wrong and are recorded here so
   they are not re-proposed: no published rc.3 exists before the positive check, and a
   post-publish install cannot gate a publication that already happened.

2. **The soak parameters, decided here rather than at 0130 -- Open, and answer it before rc.3
   ships.** How long the integration window runs, what counts as qualifying use (someone actually
   installing rc.3, not elapsed days), where the evidence lives, and what class of defect resets
   the clock. Writing these down after the fact is how a soak becomes "it felt fine". 0130
   consumes this record; it must not be the one to invent it.
